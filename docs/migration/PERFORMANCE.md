# 性能验证计划（未执行）

目前只保留迁移前的低负载 Go 基线，详见 [进展记录](PROGRESS.md)。Java 尚无同条件压测结果，不能据此断言 Java 比 Go 更快或更慢，也不能把配置中的最大连接数当作已测容量。

本轮迁移没有恢复 Go 测试，也没有运行 JMeter 或其他压力测试。Java 使用有界队列、有限在途消息和慢连接关闭策略；这些用于限制过载时的资源增长，仍需要真实链路测量才能确定合适的容量参数。

用户决定恢复测试后，可以使用 JMeter 配合 WebSocket sampler。先固定客户端行为，再选择并核对 sampler 版本：每个虚拟用户维持一个长连接，发送 101 弹幕/103 点赞并持续接收广播，不能只统计发送请求的耗时。

## 对比条件

- 同一机器、相同 CPU/内存限制、基础设施版本和部署方式；记录 JVM 堆、GC、直接内存及全部进程工作集。
- 同一连接数、房间分布、发送者比例、消息大小及速率；区分单个热门房间和多个分散房间。
- 先预热，再固定时间测量，最后等待消息排空。分别统计端到端 P50/P95/P99、实际收到/应收到、漏收、重复、错误、拒绝及关闭数量。
- 单独测网关广播链路和含 MySQL 落盘的完整链路，记录消费积压及恢复速度。
- Java 在 Kafka broker 确认后才广播，原 Go 在入本地发送队列后即广播。直接对比必须标明这项可靠性差异；若要测纯实现差异，需另外设计相同确认语义的实验。

## 适合资源有限主机的顺序

1. 先用一个房间、少量连接和低发送速率核对功能与计数，不同时启动多套服务。
2. 每次只提升一个变量，达到预定的内存、延迟或错误阈值即停止；不直接以十万连接为起点。
3. 记录连接建立、稳态广播、慢消费者、断线恢复和退出各阶段，避免仅给一个平均吞吐数字。
4. 保留原始样本、配置、代码 commit 和所有服务资源占用；完成后停止本次启动的进程。

具体连接阶梯、运行时长和资源上限在恢复测试时按主机可用资源确定。上述是后续测试方案，不是已经执行的结果。
