# Java 迁移范围与架构

日期：2026-11-06。执行依据：用户已授权开始逐步修改并将每个最小、正确的提交上传到 JavaLyHn/DanmakuFlow。

## 范围

兼容 `/ws?uid=...&name=...&room=...`，类型 101 弹幕、102 房间统计、103 点赞。服务端根据连接确定用户和房间，忽略客户端伪造的用户/房间/时间字段。保留无认证的开发协议，不能将 uid 当作已经认证的身份。

使用 Java 21、Maven、Spring Boot 4、Netty 4.2、Lettuce、Kafka、MySQL、Flyway。固定实际可获取的稳定版本；基础依赖统一管理。协议模块不依赖 Spring，网关不依赖数据库模块。网关与持久化进程可独立部署。

模块：`danmaku-protocol`（协议和边界验证）、`danmaku-gateway`（连接/房间/分发与统计）、`danmaku-persistence`（批量入库/消费）、`danmaku-tools`（轻量交互客户端）。原 Go 快照置于 `legacy/go`，保留原许可证，不继续执行。

## 兼容性和可靠性

- JSON 沿用 `type/room_id/data` 和 Go 字段命名；uid 使用无符号 64 位范围，不截断到 Java long；时间支持 RFC3339 偏移及小数秒。
- 客户端点赞 `data:null` 等价于一次点赞；不接受负数/溢出。弹幕正文最多 500 个 Unicode 码点，房间最长 50 个码点；帧大小有界。
- Kafka 保存数据新增稳定 `event_id`，仅用于幂等，不冒充原先的数据库自增 id。
- 采用 Kafka broker 确认成功后发布 Redis 广播，避免明显出现“已广播但连 Kafka 都没接收”的情况。Kafka/Redis 不是原子事务；进程在两者之间退出仍可能只有存储没有直播广播。客户端重发也不是全局 exactly-once。
- 上述确认顺序比 Go 的“入本地 Kafka 队列即发布 Redis”更强，会改变延迟，性能对比必须说明这一差别。
- 数据库事务提交成功后才确认 Kafka offset。重复 event_id 可安全重放；失败保持可重试，不默默丢弃。无效记录应有明确失败策略和日志，不能无条件提交丢掉。
- Redis Pub/Sub 不提供断线补发；房间统计是短时间最终一致。online 表示连接数（同一个 uid 多连接分别计数），不擅自改变为去重人数。
- Netty I/O 线程不得执行阻塞 Redis/Kafka/数据库调用。连接写缓冲、业务队列、在途消息有界；慢连接明确关闭并计数，防止无限积压。
- 默认绑定回环地址，不自动公开服务；配置由环境变量提供，禁止提交真实口令或硬编码生产账号。
- Flyway 仅创建/增量修改表，不 DROP 现有表；不自动接管原数据库。采用独立新库，历史数据迁移单独安排。

## 验证与资源约束

不再启动 Go 测试。Java 构建串行，测试单 JVM，设置堆和处理器上限；不自动启动 Docker、MySQL、Redis、Kafka 集群。协议、房间生命周期、Netty 握手、背压、入库后提交顺序先用有限功能测试覆盖。真实基础设施未验证的部分必须在进展中明确记载，不得把模拟测试称为完整全链路测试。

没有前端/视频服务/认证体系扩展需求。原回放接口未启用，先保留历史数据访问能力，不凭空声称兼容一个不存在的线上路由。JMeter 可用于将来 WebSocket 压测（需要对应 sampler），本轮不运行压测。
